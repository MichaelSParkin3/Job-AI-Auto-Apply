# Story 5.2.1: Lever Resume-First + Analysis Wait

## Status
Ready for dev

## Story
As an operator,
I want the agent to upload the resume first and wait for Lever’s resume analysis to complete,
so that core fields are auto-populated correctly before the agent validates and fills any remaining fields, proceeding to submit only when allowed.

## Acceptance Criteria
1. Resume-first order
   - For Lever `/apply` pages in `ai_autofill`, the system uploads the resume before executing any `AutofillExecutor` field intents.
   - On success, emit telemetry `RESUME_UPLOAD_CONFIRMED` (existing) and new `RESUME_ANALYSIS_STARTED`.

2. Analysis wait with DOM cues
   - After upload, wait for a configured success/ready selector to appear OR for DOM stability (no mutations for X ms) OR for a small network-idle window.
   - Default wait window: 3–15s (configurable; profile/site overrides allowed). Jitter using existing pacing helpers.
   - Emit `RESUME_ANALYSIS_DONE` with duration on success; `RESUME_ANALYSIS_TIMEOUT` on timeout, then continue.

3. Intelligent fill after analysis
   - Re-read core inputs (name/email/phone/links) after analysis; skip fills for already-populated fields (idempotent).
   - Continue with planned custom questions and remaining fields; maintain existing artifact capture and redaction.
   - Validate auto-populated fields for correctness before proceeding:
     - name/email/phone must be non-empty and pass basic validators (email format, E.164-ish phone normalization).
     - If a field fails validation but a profile answer exists, prefer the profile value; otherwise log a `RESUME_FIELD_VALIDATION_FAILED` event and continue.
     - Emit `RESUME_FIELDS_VALIDATED` with per-field outcomes (ok/updated/failed) and value lengths only (no PII).

4. Telemetry and artifacts
   - Add analysis wait events to logs with selectors used and elapsed time.
   - Keep `AUTOFILL_FIELD_*` events; ensure preview screenshot occurs after fills (not before).

5. Configurability
   - Add site-level defaults under `sites/lever/config.yaml` (or profile overrides) for:
     - `resume.success_selectors`: array of CSS selectors for success/ready states.
     - `resume.max_wait_seconds`: integer (default 12–15s).
     - `resume.poll_interval_ms`: integer (default 250–400ms).

6. Regression tests
   - Unit: stub client that exposes a success node after a delay; assert wait behavior and telemetry.
   - Unit: confirm resume-first ordering vs. field fills.
   - Unit: timeout path proceeds without blocking and logs `RESUME_ANALYSIS_TIMEOUT`.

### Testing
- Use stub browser client exposing a success node after a delay to assert waiting logic and telemetry.
- Validate per-field outcomes without PII (value lengths only).
- Ensure preview happens after fills in `ai_autofill` mode and not before.

## Non-Goals
- CAPTCHA bypass. If a CAPTCHA appears, stop before submission and surface in preview.
- Changing domain guardrails (already enforced by Story 5.2).

## Telemetry Schema (new)
- `RESUME_ANALYSIS_STARTED`: { runId, candidateId, selectors, startedAt }
- `RESUME_ANALYSIS_DONE`: { runId, candidateId, selectors, durationMs }
- `RESUME_ANALYSIS_TIMEOUT`: { runId, candidateId, selectors, waitedMs }

## Risks & Mitigations
- Tenants vary in DOM; make selectors configurable and include a network/idle fallback.
- Longer waits can impact throughput; cap timeout and continue with best effort.

## Rollout
- Phase 1: Implement resume-first ordering + analysis wait + unit tests.
- Phase 2: Tune selectors with real snippets; document in `docs/snippets/lever-and-google-snippets.md`.
