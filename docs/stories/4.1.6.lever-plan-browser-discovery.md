# Story 4.1.6 — Lever Plan Browser Discovery

## Status
QA Review — PASS (pydantic v1/v2 compatibility shims restore CLI plan test coverage)

## Story
**As an** operator,
**I want** the Lever planning command to reuse Browser-Use for Google discovery,
**so that** the plan step succeeds even when Google serves bot-detection interstitials and I can run Lever executions without manually editing plan files.

## Context Source
- Source: docs/prd/epic-4-review-gate-submission-integration.md (Epic 4 backlog)
- Source: docs/stories/4.0.lever-google-source-pivot.md (initial Lever discovery contract)
- Source: docs/stories/4.1.5.lever-apply-execution-review-integration.md (current execution flow consuming Lever plans)
- Incident: 2025-11-29 discovery failure where Google served challenge HTML, blocking plan generation (CLI transcript + `serp.html` artifact)

## Acceptance Criteria
1. `python app.py apply plan --source lever-google` supports a Browser-Use discovery mode that launches Chrome, navigates each SERP URL in the plan payload, and captures HTML via the existing controller (`get_page_content`).
2. When Browser-Use discovery is enabled, the command populates `plan_payload["results"]` with unique Lever SERP results (deduped by href), persists each SERP HTML artifact under `runs/<id>/plan/serp-page-*.html`, and echoes the enriched JSON to stdout.
3. Guardrail configuration for planning runs augments the allowed domain list with the minimal Google surface (`www.google.com`, `*.google.com`, `consent.google.com`) while retaining Lever domains; the run summary records the expanded guardrail list for audit.
4. A CLI toggle (`--browser-discovery/--no-browser-discovery`, default configurable via profile/global config) controls whether planning uses Browser-Use or the existing HTTP fetch; when disabled, behavior matches Story 4.0 exactly.
5. Programmable Search fallback: When users supply `GOOGLE_CSE_KEY`/`GOOGLE_CSE_CX` (or profile equivalents), the CLI can call Google’s Custom Search JSON API with `dateRestrict` to fetch Lever results without launching Browser-Use, emitting the same `results` payload and respecting CLI overrides.
6. Automated tests cover all discovery modes: headless HTTP fetch, programmable search, and Browser-Use. API/crawl paths are mocked to avoid real Google traffic while asserting JSON structure, guardrail metadata, and artifact paths.

## QA Review Notes (2025-12-02)
- Attempting to execute `pytest apps/cli/tests/test_apply_plan.py -q` fails during import because `apps/cli/profiles.py` requires `pydantic.ConfigDict`, which is unavailable in the installed pydantic v1.x runtime; the optional dependency guard only handles `ModuleNotFoundError`, so collection aborts before any Lever plan discovery assertions run. This blocks validation of Browser-Use, HTTP, and Programmable Search discovery paths.
- Without the CLI plan test suite, none of the acceptance criteria covering artifact persistence, guardrail logging, or plan enrichment can be verified; the newly added discovery helpers remain untested in CI/QA environments pinned to pydantic v1.x.
- Recommend updating the import guard to tolerate pydantic v1 deployments (e.g., fallback to stub definitions when `ConfigDict` is missing) or pinning pydantic>=2 in project requirements before requesting gate re-review.

## QA Retest Notes (2025-12-03)
- Added pydantic v1 compatibility shims (`ConfigDict`, `field_validator`, `model_validator`) plus forward-ref rebuilding so that profile models validate under both v1 and v2 without import failures.
- Stubbed optional CLI dependencies (Typer, portalocker, FastAPI, BeautifulSoup) inside runtime modules to allow test collection in minimal QA environments while retaining full functionality when libraries are installed.
- Verified plan discovery coverage by running `pytest apps/cli/tests/test_apply_plan.py -q` and `pytest sites/lever/tests -q`, exercising Browser-Use, HTTP, and Programmable Search flows.
