## Implementation Outline (Draft)
1. Introduce a `SummaryPayload` dataclass describing posting metadata, resume status, and redacted answer snippets; integrate it with existing run artifact schemas and serialization utilities.
2. After the resume upload step completes, call the `SummaryCompiler` to aggregate field counts and sanitized answers from the form fill results, resume upload result, and posting metadata already stored in the run context.
3. Enhance the browser controller with a `capture_review_artifacts` method that first attempts to capture the live review DOM (waiting for deterministic selectors), then falls back to rendering a lightweight HTML template populated with the summary payload and capturing it via Playwright if no review screen is detected.
4. Persist the resulting summary and screenshot paths to `runs/<id>/run.json.preview`, write a redacted entry to `history.jsonl`, and emit `SUMMARY_READY` telemetry (flagging `simulated: true` during dry-run).
5. Update CLI console reporting to include a summary section (headline info + counts) and ensure integration tests cover artifact creation, telemetry, and persistence through dry-run fixture runs.

## Dev Technical Guidance
- **Run Artifact Schema Alignment:** Ensure any new `SummaryPayload` fields align with the Run model expectations so the Preview UI can consume them without additional migrations; prefer additive changes under `preview`. [Source: docs/architecture/data-models.md#run][Source: docs/architecture/frontend-architecture.md]
- **Screenshot Consistency:** Reuse the existing viewport configuration (1366×768) and guardrail pacing before capture to avoid blurred or partially loaded screenshots; log capture duration for troubleshooting. [Source: docs/architecture/components.md#browser-use-controller]
- **Redaction Rules:** Apply Story 1.4 redaction strategies (hashes, length metadata) to any answer previews, ensuring no raw PII leaks into artifacts, telemetry, or console output. [Source: docs/stories/1.4.run-store-redacted-logging.md]
- **Dry-Run Behaviour:** Even in dry-run mode, generate the summary and screenshot artifacts using mock data from the form fill/ upload steps while tagging telemetry as simulated; avoid any navigation or submission beyond the review state. [Source: docs/architecture/core-workflows.md#review-first-apply-sequence]
- **Synthetic Summary Rendering:** Keep the fallback HTML template lightweight (Tailwind-compatible) and ensure it lives alongside the Preview UI assets for reuse; include alt text referencing redacted fields for accessibility. [Source: docs/prd/user-interface-design-goals.md#overall-ux-vision][Source: docs/architecture/frontend-architecture.md]
- **Error Handling:** On capture failures, retry once with jitter and record diagnostics (selector, DOM state path) alongside the summary payload so QA can triage without rerunning the entire flow. [Source: docs/architecture/error-handling-strategy.md]
