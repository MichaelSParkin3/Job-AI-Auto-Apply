# Story 2.3 — Profile Binding & Resume Availability

## Status
QA Gate: PASS — Ready for Release

## Story
As a user,
I want the active profile bound to the browser session,
so that identity and documents are correctly scoped.

## Context Source
- Source Document: docs/prd/epic-2-stealth-browser-wrapper-profiles.md#story-23--profile-binding--resume-availability

- Existing System Impact: Builds on Story 2.1’s Browser-Use bootstrap and Story 2.2 guardrails by ensuring `apply` commands honor validated profile assets (resume, session dir, overrides) and expose profile metadata to downstream automation without leaking PII.

## Acceptance Criteria
1. Launching `python app.py apply open <search_url>` uses the selected/active profile to resolve `user_data_dir`, Browser-Use model, locale/timezone, viewport, and guardrail overrides; precedence remains CLI → profile → global defaults, and telemetry reflects the bound profile id. [Source: docs/prd/epic-2-stealth-browser-wrapper-profiles.md#story-23--profile-binding--resume-availability][Source: docs/prd/requirements.md#functional-fr][Source: docs/architecture/components.md#browser-use-controller][Source: apps/cli/main.py]
2. The resume path resolves to `data/resumes/<profile>/resume.pdf` (absolute on Windows after resolution); if the PDF is missing or unreadable, the CLI surfaces a structured, actionable error before launching Browser-Use and logs a guardrail warning without starting Chrome. [Source: docs/prd/epic-2-stealth-browser-wrapper-profiles.md#story-23--profile-binding--resume-availability][Source: docs/prd/requirements.md#functional-fr][Source: docs/stories/1.3.profiles-schema-commands.md][Source: apps/cli/profiles.py]
3. The Browser-Use wrapper receives profile metadata (id, display name, resolved resume path, QA overrides, browser overrides) so later automation can map fields; the JSON payload returned by `apply open` includes a `profile` object with these details (resume path redacted in logs per policy). [Source: docs/prd/epic-2-stealth-browser-wrapper-profiles.md#story-23--profile-binding--resume-availability][Source: docs/architecture/data-models.md#profile][Source: docs/prd/requirements.md#functional-fr][Source: docs/architecture/security-and-performance.md]
4. `python app.py profiles current` reports the active profile id, validation status, resolved session directory, and resume presence so operators can confirm bindings before running automation. [Source: docs/prd/epic-2-stealth-browser-wrapper-profiles.md#story-23--profile-binding--resume-availability][Source: docs/prd/requirements.md#functional-fr][Source: apps/cli/profiles.py]
5. Automated tests cover switching between at least two profiles, verifying that `apply open` binds unique `user_data_dir` directories, surfaces resume-missing errors, and does not leak metadata between runs. [Source: docs/prd/epic-2-stealth-browser-wrapper-profiles.md#story-23--profile-binding--resume-availability][Source: docs/architecture/testing-strategy.md][Source: core/tests/test_apply_open.py]

## Implementation Outline (Draft)
- Introduce a `ProfileBinding` dataclass in `apps/cli/profiles.py` that resolves and caches resume path, session directory, and overrides, and provides JSON/telemetry views with PII redaction for logging.
- Refactor `apply open` to require a valid binding before instantiating `BrowserUseController`, short-circuiting with a structured error if validation fails while keeping dry-run fallback for demo profile only.
- Pass the binding into `BrowserLaunchConfig` so `_base_payload` includes profile metadata; store the binding alongside run context to unlock downstream field mapping and resume upload orchestration.
- Standardize CLI outputs (`profiles current`, `profiles list`, `apply open`) on the binding structure to keep operators informed and reduce drift between commands.
- Extend tests to simulate multi-profile switching, assert error handling for missing resumes, and confirm binding metadata appears in CLI JSON without polluting guardrail logs with PII.
