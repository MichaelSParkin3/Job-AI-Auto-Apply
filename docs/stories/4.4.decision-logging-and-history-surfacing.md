# Story 4.4 — Decision Logging & History Surfacing

## Story
**As a** compliance stakeholder,
**I want** every human or AI review decision captured with auditable summaries in run artifacts and history,
**so that** upcoming autonomy modes remain reviewable and trustworthy without leaking sensitive information.

## Acceptance Criteria
1. **History Entry Expansion** — Each appended `history/history.jsonl` record persists the originating run `mode`, a `decisions` summary object (per-outcome counts plus latest timestamps), and `queueDepth` metrics (pending, escalated, decided) without breaking existing schema-required fields. [Source: docs/prd/epic-4-review-gate-submission-integration.md#story-44-decision-logging--history-surfacing][Source: docs/architecture/database-schema.md#historyentry--historyhistoryjsonl]
2. **Run Artifact Audit Trail** — `runs/<id>/run.json` stores an append-only `decisions[]` array and rolling `queue` snapshots that reference persisted prompt/plan artifacts (`runs/<id>/decisions/*`, `runs/<id>/lever/<candidate>/`). Data mirrors the `SubmissionDecision` contract (`outcome`, `confidence`, `mode`, `rationaleHash`, `timestamp`) so the preview queue and CLI remain consistent. [Source: docs/prd/epic-4-review-gate-submission-integration.md#story-44-decision-logging--history-surfacing][Source: docs/architecture/database-schema.md#runrecord--runsidrunjson][Source: docs/architecture/core-workflows.md#run-modes--decision-flow]
3. **CLI History Summaries** — `python app.py history --last` (and `--limit n`) renders decision aggregates per run (approved, escalated, aborted, needs_review) with timestamps and run mode, sourcing the new history payloads while keeping prior flags (status, profile, posting) intact. [Source: docs/prd/epic-4-review-gate-submission-integration.md#story-44-decision-logging--history-surfacing][Source: docs/prd/requirements.md#functional-fr]
4. **Redacted Rationale Logging** — Decision persistence hashes or tokenizes free-text rationales before writing to `actions.log`, `history.jsonl`, or CLI output, recording when redaction occurred so no raw PII escapes while still enabling audit correlation. [Source: docs/prd/epic-4-review-gate-submission-integration.md#story-44-decision-logging--history-surfacing][Source: docs/architecture/security-and-performance.md#security-requirements][Source: docs/stories/1.4.run-store-redacted-logging.md]
5. **Atomic Append Regression Coverage** — Automated tests exercise high-volume decision payloads to confirm `HistoryWriter` maintains Windows-safe, atomic appends (lock, flush, rename) and rolls back on failure, covering concurrent append scenarios introduced by richer records. [Source: docs/prd/epic-4-review-gate-submission-integration.md#story-44-decision-logging--history-surfacing][Source: docs/prd/technical-assumptions.md#additional-technical-assumptions-and-requests][Source: docs/stories/1.4.run-store-redacted-logging.md]

## Dev Technical Guidance
- **Decision Contract Alignment:** Reuse the canonical `SubmissionDecision` schema when persisting decisions to avoid divergent fields; include `mode` to distinguish human vs AI actions for upcoming Epic 5. [Source: docs/architecture/database-schema.md#runrecord--runsidrunjson][Source: docs/architecture/core-workflows.md#run-modes--decision-flow]
- **Redaction Strategy:** Prefer deterministic hashing (e.g., SHA-256 + prefix) for rationale bodies and store only hashes plus length/classification metadata; logs should indicate `"rationale_redacted": true` to satisfy compliance review. [Source: docs/architecture/security-and-performance.md#security-requirements][Source: docs/stories/1.4.run-store-redacted-logging.md]
- **Artifact Referencing:** Store prompt/plan paths relative to the run directory (e.g., `decisions/<candidateId>/prompt.json`) and mirror references in both `run.json` and history entries so auditors can trace evidence quickly. [Source: docs/architecture/backend-architecture.md#database-architecture-file-repository]
- **Concurrency & Atomicity:** Continue using file locks + temp-file renames for `history.jsonl`; ensure new aggregation steps happen in-memory before the atomic write to minimize critical section duration. [Source: docs/prd/technical-assumptions.md#additional-technical-assumptions-and-requests]
- **CLI UX Considerations:** History command should support both tabular console output and `--json` for automation, while paginating runs to maintain performance with enriched payloads. [Source: docs/prd/requirements.md#functional-fr]
- **Regression Awareness:** Changes rely on Story 4.3 queue state; avoid mutating Zustand or preview APIs beyond read-only fetches when computing aggregates. [Source: docs/stories/4.3.preview-ui-queue-drawer-and-keyboard-flow.md]
