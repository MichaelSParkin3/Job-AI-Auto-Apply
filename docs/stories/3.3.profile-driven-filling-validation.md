# Story 3.3 — Profile-Driven Filling & Validation

## Story
As an applicant,
I want fields filled from my active profile with sensible defaults and safety checks,
so that answers are accurate and consistent.

## Acceptance Criteria
1. **Plan-Driven Fill Execution** — Introduce a form fill executor that consumes the persisted `FormFillPlan` from Story 3.2, iterates Quick Apply steps in order, and issues deterministic DOM actions (type, select, click) via `BrowserUseController` without regenerating HTML snapshots. Each mapped entry must confirm the element is interactable before entering values, respecting guardrail pacing and emitting granular telemetry (`FIELD_FILL_STARTED`, `FIELD_FILLED`, `FIELD_SKIPPED`). [Source: docs/prd/epic-3-simplyhired-quick-apply-automation.md#story-33-profile-driven-filling-validation][Source: docs/stories/3.2.form-structure-mapping-selector-library.md][Source: apps/browser/controller.py]
2. **Profile Value Resolution & Normalisation** — Populate contact, eligibility, and identity fields from the active profile’s YAML (`identity`, `qa_overrides`, `documents`) with deterministic transforms: trim whitespace, normalise phone numbers to E.164-like `+1 555 555 5555`, ensure emails lower-case, and redact/omit sensitive substrings when previewing values. Null or missing profile data yields a skip with diagnostics rather than placeholder text. [Source: docs/prd/epic-3-simplyhired-quick-apply-automation.md#story-33-profile-driven-filling-validation][Source: apps/cli/profiles.py][Source: apps/cli/redaction.py]
3. **Widget-Specific Handling** — Support text inputs/areas, selects, radios, and checkboxes using the plan metadata: radio/select options are matched by normalised synonym comparison against profile answers and `qa_overrides`; free-text areas fall back to concise template summaries pulled from profile narrative fields without leaking resume content. Unsupported widgets or confidence < threshold are skipped with structured reasons logged. [Source: docs/prd/epic-3-simplyhired-quick-apply-automation.md#story-33-profile-driven-filling-validation][Source: docs/stories/3.2.form-structure-mapping-selector-library.md][Source: docs/snippets/simply-hired-snippets.md#simplyhired-apply-modal---custom-employer-questions]
4. **Telemetry, Redaction, and Persistence** — For every field attempt, emit `FIELD_FILLED`/`FIELD_SKIPPED` events through `log_event` with redacted `valuePreview`, `selector`, `step`, `profileId`, and `reason`; update `run.json`/`history.jsonl` with a `formFill` summary capturing filled vs skipped counts while keeping PII masked per Story 1.4 policies. [Source: docs/prd/epic-3-simplyhired-quick-apply-automation.md#story-33-profile-driven-filling-validation][Source: apps/cli/utils.py][Source: apps/cli/run_store.py][Source: docs/stories/1.4.run-store-redacted-logging.md]
5. **Guardrails & Submission Safety** — Dry-run and review modes must halt before any submit button interaction; live modes stage the form for Story 3.4 but still refrain from triggering submission in this epic. Browser guardrails stay enforced (single-tab, domain allowlist), and retries for transient interaction failures are capped (e.g., one retry per field) with `FIELD_RETRY` telemetry. [Source: docs/prd/epic-3-simplyhired-quick-apply-automation.md#story-33-profile-driven-filling-validation][Source: docs/architecture/components.md#browser-use-controller][Source: docs/architecture/error-handling-strategy.md]
6. **Validation Feedback & Diagnostics** — After filling, validate required fields for non-empty values where selectors expose them (e.g., input `value`, radio checked state). Summarise issues in a per-step diagnostics block appended to artifacts, and surface a CLI console table listing skipped/errored fields with actionable reasons to aid reviewers. [Source: docs/prd/requirements.md#functional-fr][Source: docs/architecture/testing-strategy.md][Source: apps/cli/main.py]

## Implementation Outline (Draft)
1. Parse persisted `FormFillPlan` artifacts once and construct a `FormFillExecutor` with `BrowserUseController` and `ProfileAnswerResolver` dependencies. Cache selectors to avoid repeated DOM queries.
2. For each mapped field, request the resolved answer; if unavailable, log `FIELD_SKIPPED` with reason `profile_missing` and diagnostics from the plan. Otherwise, invoke the widget-specific handler with guardrail-safe Browser-Use commands, retrying once on recoverable errors (timeouts, focus issues). Each success logs `FIELD_FILLED` with a redacted `valuePreview` (first 12 chars / masked) and updates the in-memory result.
3. After processing a step, read back DOM values where feasible (e.g., `input.value`, `select.value`, `textarea.value.length`) to validate required fields, logging warnings and marking them as `validation_failed` if empty.
4. Aggregate the executor result into a `formFill` payload: counts, filled/skipped arrays (with masked previews), per-step diagnostics, and attach references to source plan artifacts. Persist to `run.json`, append to history, and print a CLI summary table. Emit a closing `FORM_FILL_COMPLETE` telemetry event summarising counts.
5. Update documentation to explain the fill pipeline, redaction rules, and how to customise answers via profile YAML or override JSON files, ensuring developers monitor Browser-Use release notes before adjusting DOM interactions.

## Dev Technical Guidance
- **Profile Schema Alignment:** Reuse `ProfileBinding` from `apps/cli/profiles.py` to access normalised paths and QA overrides. Ensure new resolver utilities accept both global config and profile-level overrides for future epics. [Source: apps/cli/profiles.py][Source: docs/architecture/data-models.md#profile]
- **Answer Normalisation:** Centralise phone/email formatting helpers to prevent duplication and to maintain redaction compatibility. Reference `apps/cli/redaction.py` when building previews to ensure regex patterns remain effective. [Source: apps/cli/redaction.py]
- **Browser-Use Safety:** All DOM interactions must call guardrail-aware controller methods; avoid raw JS injection outside the controller to maintain pacing and telemetry. Document any additional Browser-Use APIs touched and gate them behind configuration flags if unstable. [Source: docs/architecture/components.md#browser-use-controller]
- **Plan Integrity:** Treat `FormFillPlan` as read-only. If selectors fail, log diagnostics without mutating the plan artifact; future epics rely on reproducible artifacts for auditing. [Source: docs/stories/3.2.form-structure-mapping-selector-library.md]
- **Telemetry Hygiene:** Keep event payloads small and redaction-friendly (e.g., store only value hashes or masked previews). Validate via unit tests that `log_event` output excludes raw PII. [Source: apps/cli/utils.py][Source: docs/stories/1.4.run-store-redacted-logging.md]
- **CLI UX:** Align console summaries with existing Typer patterns (colours, tables) so dry-run testers can quickly spot skipped fields without combing logs. [Source: docs/prd/requirements.md#functional-fr]
