# Story 3.5 — SimplyHired Quick Apply: Live Debugging Notes

This document captures our investigation, fixes, and guidance for the Story 3.5 flow: building a submission summary and capturing a pre‑submit screenshot while driving SimplyHired “Quick Apply” in live mode.

Scope covers the CLI path `apply open` and the discovery → form mapping → resume upload portion, with emphasis on reliably entering the on‑platform (Indeed Smart Apply) path rather than the off‑platform employer site.

— Last updated: 2025‑09‑29

- CLI entry and flow orchestration: `apps/cli/main.py`
- Browser controller wrapper: `apps/browser/controller.py`
- Quick Apply discovery logic: `sites/simplyhired/quick_apply_discovery.py`

- OS: Windows
- Python: `python -V` (observed 3.10 / 3.13 in different shells)

  - `python app.py profiles new frontend-live`
  - Ensure resume exists at `data/resumes/frontend-live/resume.pdf`

```yaml
  allowed_domains:

    - "smartapply.indeed.com"

```

## Symptoms We Saw

1) Early runs “stuck” at search page, or failing discovery with AttributeError.
2) Later, discovery clicked a link that opened an off‑platform employer site rather than Indeed’s “Smart Apply” (Quick Apply) UI.
3) Resume upload then failed with `UPLOAD_FAILED: not_found` because no on‑platform form existed.
4) After closing the browser manually, we saw cascading `evaluation_failed`/`no close frame` errors.

## Timeline of Fixes

1) Missing method: `_trigger_quick_apply` raised `AttributeError`.
   - Added implementation in `sites/simplyhired/quick_apply_discovery.py`.

2) Test snapshot advancement (RecordingClient):
   - Avoided auto‑triggering clicks in tests to prevent advancing fixtures unexpectedly.
   - Split behavior: tests/dry‑run vs live (see “Live vs Dry‑run Heuristics”).

3) Off‑platform apply link clicked:
   - Root cause: the same `data-testid=viewJobHeaderFooterApplyButton` identifies both off‑platform and Quick Apply anchors; off‑platform anchors route via `/out?...`.
   - Changes:
     - Prefer a visible Quick Apply affordance (bolt icon) before generic anchors:
       - First try `button[data-testid=viewJobHeaderFooterApplyButton]` (if present).
       - Then `a[data-testid=viewJobHeaderFooterApplyButton] svg[data-icon='bolt-lightning']` (anchor with bolt icon).
       - Then `a[data-testid=viewJobHeaderFooterApplyButton]:not([href^='/out'])`.
       - Only then fallback to any other known selectors.
     - Allowlist `smartapply.indeed.com` to permit the redirect for on‑platform Quick Apply.

4) Post‑click URL probing failed with `'_run' not found`:
   - Our initial URL probe used an event‑loop helper not available in this context.
   - Fixed `apps/browser/controller.py:get_current_url()` to use client shims (e.g., `page.url`) and log `browser.url`.

## Live vs Dry‑run Heuristics

- Dry‑run / tests: treat presence of the apply control as “modal” for counting and do not click (preserves fixture order and counts).
- Live:
  - Do not treat “apply control present” as open.
  - Attempt an ordered click (bolt/btn first), then verify either:
    - URL contains `smartapply.indeed.com` or `indeedapply`, or
    - Inline application container renders.
  - Log each `quick_apply.url_check` attempt and `QUICK_APPLY_URL_CONFIRMED` or `QUICK_APPLY_INLINE_CONFIRMED`.

## Code Changes (High‑Level)

### sites/simplyhired/quick_apply_discovery.py

- Added `_trigger_quick_apply()` with ordered selector preference:

```python
preferred_selectors = [
  "button[data-testid=viewJobHeaderFooterApplyButton]",
  "a[data-testid=viewJobHeaderFooterApplyButton] svg[data-icon='bolt-lightning']",
  "a[data-testid=viewJobHeaderFooterApplyButton]:not([href^='/out'])",
  *self.selectors.detail_quick_apply,
]
```

- Live‑only post‑click poll (3x ~300ms):
  - Log current URL (`quick_apply.url_check`).
  - Confirm Smart Apply URL or inline form; log confirmation events.

- Adjusted `_detect_mode()`:
  - Tests/dry‑run may count “modal” when the apply control exists.
  - Live waits for inline container after click; otherwise returns `None` and continues polling.

### apps/browser/controller.py

- Added `get_current_url()` that uses client shims (e.g., Playwright `page.url`) and logs `browser.url`.

### data/profiles/frontend-live.yaml

- Added `browser.allowed_domains` entries for `smartapply.indeed.com` and `www.indeed.com`.

All tests pass after these changes (`pytest -q`).

## How to Reproduce & Inspect

1) Run live discovery with a simple query and `-n 1`.
2) Open `runs/<run-id>/actions.log` and search for:
   - `QA_CANDIDATE` → we’re evaluating a job item.
   - `QUICK_APPLY_TRIGGERED` → which selector was clicked.
   - `quick_apply.url_check` → actual URL after click.
   - `QUICK_APPLY_URL_CONFIRMED` or `QUICK_APPLY_INLINE_CONFIRMED`.
3) If we didn’t reach on‑platform:
   - Inspect `runs/<run-id>/quick-apply/candidate-01.html` and copy the header/footer apply container for that job (the element near the bolt icon/“Quick Apply”).
   - Share the first few `quick_apply.url_check` lines (it reveals whether we were still at SimplyHired or redirected elsewhere).

## Why Off‑Platform Happens

SimplyHired uses the same `data-testid=viewJobHeaderFooterApplyButton` for both “Quick Apply” (Indeed Smart Apply) and the off‑site employer application. The visible bolt icon and later destination are the differentiators. That’s why selector ordering and URL/inline verification are necessary.

## Current Guidance

- Keep the domain allowlist synced with the destinations we intend to support (e.g., `smartapply.indeed.com`).
- Prefer clicking the bolt‑icon variant or a button; avoid generic anchors that route off‑site.
- Use actions.log confirmation events to debug where we landed.

## Next Steps (Optional Hardening)

1) Extend post‑click poll to 5 attempts (~1.5s) if flakiness observed.
2) Add Smart Apply root detection (e.g., known container attribute) for a positive on‑platform signal.
3) Enhance search‑readiness variant matching if testids change (update `sites/simplyhired/selectors/…`).
4) Add CLI flag to override attempt_trigger per run: e.g., `--no-qa-trigger` for diagnostic runs.
5) Log final resolved destination in `run.json` discovery payload for later analytics.

## Known Pitfalls

- Closing the browser mid‑run triggers follow‑up `evaluation_failed` and “no close frame” errors; rely on early part of the log for root cause.
- Some jobs display the Quick Apply badge but only provide an off‑site path in certain regions/ab tests; URL confirmation will make it visible.

## Tries & Findings — 2025-09-29 (Live)

This tracks what we tried today to reach Indeed Smart Apply reliably and what actually happened in live runs.

### Changes Implemented
- Browser URL visibility
  - Added `BrowserUseController.get_current_url()` and adapter support so we can log `quick_apply.url_check` instead of seeing `browser.url.failed: url_unavailable`.

- Selector hardening (avoid off‑platform clicks)
  - Preferred selectors now try: button → bolt icon in anchor (non-`/out`) → non-`/out` anchor → fallbacks.
  - Added pre-filter to skip anchors that resolve to disallowed domains.

- Redirect preflight and direct `/out` navigation
  - Added a redirect preflight helper (`resolve_redirect`) to test `/out` targets without navigating.
  - Per request, also added a direct `/out` navigation path: when the anchor `href`/`data-mdref` begins with `/out`, we build an absolute `https://www.simplyhired.com/out?r=…` and navigate to it, then confirm where we landed.

- Simple click mode
  - New CLI flag `--simple-click` to mimic a straightforward user click: prefer the bolt icon inside the anchor, then the anchor itself, with no pre-filtering or preflight.

### Evidence From Runs
- Run `20250929-181802-e53675b1`
  - Sequence: `QUICK_APPLY_TRIGGERED` (bolt) → three `browser.url.failed` (`url_unavailable`) → `QUICK_APPLY_MISSING`.
  - Interpretation: URL retrieval missing at that time (fixed later by adding `get_current_url`).

- Run `20250929-184918-b8a5ba88`
  - Fallback clicked anchor. `quick_apply.url_check` (attempts 1–5) →
    `https://ats.rippling.com/conceptplus/jobs/c4d52663-888c-48c8-a295-8613bb2a5084?jobSite=Indeed`.
  - Outcome: `QUICK_APPLY_MISSING`. Off‑platform destination even though labeled “Quick Apply”.

- Run `20250929-185341-f6ec9be0`
  - Pre-filter logged `QUICK_APPLY_SELECTOR_SKIPPED_OFFSITE` for `/out?r=…`.
  - No safe trigger found → `QUICK_APPLY_MISSING`.

- Run `20250929-191017-f5139e88`
  - Direct `/out` navigation enabled (per request):
    `guardrail.browser.NAVIGATE` → `https://www.simplyhired.com/out?r=c72dGJX…` → `QUICK_APPLY_OUT_NAVIGATED`.
  - `quick_apply.url_check` immediately reported the final URL as the same Rippling ATS URL as above.
  - Conclusion: that job’s `/out` token resolves to Rippling (not Smart Apply) in our session.

### User Manual Trace (Reference)
- Manual browser network logs for a different job show:
  - GET `https://www.simplyhired.com/out?r=…` →
  - GET `https://smartapply.indeed.com/beta/indeedapply/applybyapplyablejobid?...` →
  - Lands at Smart Apply form (e.g., resume-selection).
- Takeaway: the `/out` token can resolve either to Smart Apply or to an external ATS depending on the posting and session.

### Current Hypothesis
- The `data-testid=viewJobHeaderFooterApplyButton` anchor is reused for multiple destinations. Its `/out?r=…` token is job‑specific and sometimes resolves to ATS instead of Smart Apply. AB tests, cookies, geo, or job configuration influence the final redirect.

### Where We Are (Problem Statement)
- We mirrored both strategies (filtered click, direct `/out` navigation, and pure “simple click”) and still observed ATS destinations for today's candidate. That means the button for that posting does not route to Smart Apply in our automation session.

### Options Going Forward
- Smart‑Apply‑only gate (recommended for automation)
  - Preflight `/out` (or post‑click check) and continue only when final host is `smartapply.indeed.com` or URL contains `indeedapply`. Otherwise skip the job.

- Keep “simple click” but bail quickly
  - After clicking or navigating to `/out`, if `current_url` is not Smart Apply within N attempts, navigate back and mark `QUICK_APPLY_OUT_NOT_SMARTAPPLY`.

- Diagnostics to capture
  - On any `/out` path: record both the raw token (`href`/`data-mdref`) and the resolved final URL.
  - When Smart Apply succeeds, capture the first `applybyapplyablejobid` URL (includes `indeedApplyableJobId`, `iaUid`) for future positive detection.

### New Flags / Controls
- `--simple-click`: mimic a human click (bolt → anchor → button), no preflight.
- Proposed: `--only-smartapply` (to implement): enforce gate to accept only Smart Apply destinations.
