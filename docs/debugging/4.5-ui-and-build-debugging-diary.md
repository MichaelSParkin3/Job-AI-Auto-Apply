# Debugging Diary: Epic 4.5 UI and Build Issues

This document outlines the series of issues encountered and steps taken while trying to enable the review UI for an existing application run.

## Initial Goal
The user wanted to test the new features from Epic 4, specifically the `apply run` command for Lever and the human review queue UI.

---

## Problem 1: No Command to View an Existing Run

### Symptoms
- The user executed `python app.py apply run ...`.
- The command completed successfully, populating a `runs/<run_id>` directory.
- No web UI was launched, leaving no way for the user to access the review queue.

### Debugging Process
1.  My initial analysis of `apps/cli/main.py` was incorrect. I believed a `preview start` or `preview run` command existed to view existing runs. I suggested these commands, but they both failed with "No such command".
2.  After a thorough re-reading of `apps/cli/main.py`, I confirmed that while `apply demo` and `preview demo` call the `run_preview_service` function, no command was exposed to call this service for an *existing* run ID.
3.  The CLI workflow was broken: it allowed creating runs but not viewing them.

### Solution
A workaround was created by writing a new script, `serve_preview.py`, in the project root. This script manually bootstraps the necessary components to launch the preview server for a given run ID.

**`serve_preview.py`:**
```python
import sys
import typer
from apps.cli.config_loader import Settings
from apps.cli.run_store import RunStore
from apps.preview.runner import run_preview_service

def main(run_id: str):
    """
    Starts the preview server for a specific, existing run.
    """
    print(f"Attempting to start preview for run: {run_id}")
    settings = Settings.load()
    run_store = RunStore()
    try:
        run_record = run_store.load_run_record(run_id)
    except FileNotFoundError:
        print(f"Error: Run with ID '{run_id}' not found.")
        raise typer.Exit(code=1)

    print(f"Found run record for profile: {run_record.profile_id}")

    run_preview_service(
        settings,
        demo=False,
        open_browser=True,
        run_record=run_record,
        run_store=run_store,
        history_writer=None,
        run_context=None
    )

if __name__ == "__main__":
    if len(sys.argv) != 2:
        print("Usage: python serve_preview.py <run_id>")
    else:
        typer.run(main)
```

## Problem 2: React UI Crash on Load (React Error #31)

### Symptoms
- After launching the server with `serve_preview.py`, the browser opened but the UI was blank.
- The browser's developer console showed "Uncaught Error: Minified React error #31", indicating the code was trying to render a plain JavaScript object.
- The server logs showed the UI was making a `POST /api/run/preview` request.

### Debugging Process
1.  The API endpoint `POST /api/run/preview` is designed to create a *new demo run*. The UI should have been fetching data for the existing run.
2.  This confirmed the UI was not aware of the existing run context provided by the backend; it was hardcoded to behave as if in a demo mode.
3.  The fix required modifying the backend to provide an endpoint to get the "current" run's data and modifying the frontend to call it.

### Solution
A three-part fix was implemented:

1.  **Backend (`apps/preview/main.py`):** A new endpoint `GET /api/run/current` was added to return the data for the run loaded by the server.
2.  **API Layer (`apps/ui/src/lib/api.ts`):** The `createPreviewRun` function was renamed to `fetchCurrentRun` and changed to call the new `GET /api/run/current` endpoint.
3.  **UI (`apps/ui/src/App.tsx`):** The component's startup logic was changed to call the new `fetchCurrentRun` function instead of the old one.

## Problem 3 & 4: UI Build Failures & Misconfiguration

### Symptoms
- After applying the code fixes for Problem 2, the `pnpm run build` command failed.
- **Error 1**: `Rollup failed to resolve import "/src/main.tsx" from "index.html"`.
- **Error 2 (after fixing Error 1)**: The React Error #31 persisted, indicating the old, buggy code was still being served.

### Debugging Process
1.  **Resolving Error 1**: The project has an unconventional structure where `index.html` and `vite.config.ts` are in the project root, but the UI source is in `apps/ui/src`. The build failed because Vite couldn't resolve the absolute path `/src/main.tsx`.
    -   **Solution**: A `resolve.alias` was added to `vite.config.ts` to map `/src` to the correct `apps/ui/src` directory.
2.  **Resolving Error 2**: The React error persisted because of a second misconfiguration. The Vite config was building the UI to a `/dist` directory in the project root, but the Python server (`apps/preview/main.py`) was configured to serve static files from `/apps/ui/dist`. The server was still serving the *old* build.
    -   **Solution**: The `build.outDir` in `vite.config.ts` was changed from `dist` to `apps/ui/dist` and the Vite `base` was set to `/ui/` so asset URLs match the FastAPI mount (e.g., `/ui/assets/...`).

**Final `vite.config.ts`:**
```typescript
import { defineConfig } from "vite";
import react from "@vitejs/plugin-react";
import path from "path";

export default defineConfig({
  base: "/ui/",
  plugins: [react()],
  resolve: {
    alias: {
      '/src': path.resolve(__dirname, 'apps/ui/src')
    }
  },
  build: {
    outDir: "apps/ui/dist",
    emptyOutDir: true,
    rollupOptions: {
      input: path.resolve(__dirname, "index.html"),
    },
  },
  server: {
    port: 5173,
  },
});
```

## New Issue: UI loads but `/api/run/current` returns 404

### Current Symptoms
- `/ui` and assets return 200 OK.
- The first UI request to `/api/run/current` returns 404 with a JSON error payload like `{"error": {"code": "run_not_found", ...}}`.

### Why this happens
- The preview server must know which run is "loaded" for the session. When started via `python app.py preview run <run-id>`, it loads the run into app state and should mark the session as persistent so `GET /api/run/current` can read it.
- If the persistent flag isn’t recognized at runtime (or a different process is serving), the handler replies with 404.

### Quick Triage Checklist
1. Verify you started the preview against the intended run
   - Command: `python app.py preview run <run-id>`
   - Console should print: `Starting preview server for run <run-id> (profile=..., port=....)`
2. Confirm only one preview server is running on the expected port
   - Stop all Python servers (CTRL+C). Re-run the command once.
3. Hit the explicit run endpoint to prove the run is addressable
   - Open: `http://localhost:<port>/api/run/<run-id>`
   - Expected: 200 JSON with `id: <run-id>`
   - If this is 200 but `/api/run/current` is 404, the run is loaded but the session isn’t marked as current (see Step 6).
4. Confirm UI build targets the `/ui` base
   - Build result should contain `/ui/assets/index-*.js` in `apps/ui/dist/index.html`.
   - If not, re-run `pnpm run build`.
5. Verify the server is serving the correct static bundle
   - `apps/preview/runner.py` uses `apps/ui/dist`. Confirm files exist and are recent.
6. Ensure the preview service marks the session as persistent
   - In `apps/preview/main.py`, the app sets `app.state.persistent = True` when a run is passed in.
   - The `GET /api/run/current` handler should check `app.state.persistent` (not a stale closure variable) before returning 404.
   - If you previously modified this, re-run the server so the new code is live.

### Step-by-Step Recovery Plan
1. Stop any running preview servers (CTRL+C).
2. Rebuild the UI to ensure fresh assets and correct base URLs:
   - `pnpm run build`
3. Start the preview server for the specific run ID:
   - `python app.py preview run <run-id>`
4. Visit `http://localhost:<port>/ui/` in your browser.
5. If the UI shows an error banner and the server logs `GET /api/run/current 404`:
   - Open `http://localhost:<port>/api/run/<run-id>` in a new tab.
   - If that returns 200, refresh the UI tab (it should initialize on the now-warm session state).
6. If `/api/run/<run-id>` also fails:
   - Verify the run exists: check `runs/<run-id>/run.json`.
   - If missing/corrupt, choose another existing run or create a new run, then use its ID with `preview run`.
7. Optional debug: add a one-line log in `apps/preview/main.py` to print `app.state.persistent` and the loaded `run_record.id` at startup, then re-run to confirm the server is loading the run you expect.

### Known Good Signals
- Server log includes: `Starting preview server for run <run-id> ...` and later `GET /api/run/current 200`.
- Hitting `GET /api/run/<run-id>` returns full run state.
- The UI header shows "Review & Decide" and the queue drawer loads without a red error banner.

## Route Matching Edge Case: `/api/run/current` vs `/api/run/{run_id}`

### Symptom
- UI requests `/api/run/current` but receives the structured error `{ code: "run_not_found" }` instead of the “No active run found…” message. Server logs show the 404 came from the variable route handler (same message as `/api/run/{run_id}`), indicating the request was matched as if `run_id = "current"`.

### Contributing factors
- The handler used closure variables to determine whether a run was active; depending on startup timing, the closure could refer to an uninitialized context even though the app-level state was set.
- In some setups, the static route may not have been effectively consulted before the variable route; regardless, the safe fix is to make the handler tolerant and read the context from the app state.

### Fixes applied
- Backend (`apps/preview/main.py`):
  - Persist both `run_store` and `run_record` on `app.state`.
  - Add `_get_context()` to always resolve the live run context from `app.state` (falling back to closure only if needed).
  - Update `_sync_persistent_state()`, `/api/run/current`, `_assert_run()` and queue endpoints to use `_get_context()`.
- Frontend (`apps/ui/src/App.tsx`): Add a short retry loop on boot to re-attempt `/api/run/current` for transient 404s during startup.

### Confirming the fix
- After restarting the server (`python app.py preview run <run-id>`), visit:
  - `/api/run/<run-id>` → 200 JSON includes `id`, `preview`, and `queue`.
  - `/api/run/current` → 200 JSON (same structure as above).
  - `/ui/` → Loads the full "Review & Decide" UI (toolbar, preview card, queue drawer) with no red “Run not found” banner.

## Long-Term Fixes and Hygiene
- Use the official CLI command instead of the shim:
  - `python app.py preview run <run-id>`
- Keep Vite base set to `/ui/` and outDir to `apps/ui/dist` to match the FastAPI mount.
- Keep `index.html` served with `Cache-Control: no-store` during local development to avoid stale SPA shells.
- When changing preview server code, fully restart the preview process to ensure changes are applied.
- Prefer reading request-scoped state from `app.state` on the backend; avoid relying solely on closure variables in route handlers.

## Addendum — Findings & Fix Plan (2025-09-30)

### What’s still risky or brittle
- Route precedence: the dynamic route `GET /api/run/{run_id}` was defined before the static route `GET /api/run/current`. In FastAPI, declaration order matters when a literal segment overlaps a parameterized one. This can cause requests to `/api/run/current` to be handled by the `{run_id}` route, returning a structured 404 (`run_not_found`) from the wrong handler.
- SPA shell caching under `/ui`: we already set `Cache-Control: no-store` for `/` (the explicit `FileResponse(index.html)`), but we actually navigate to `/ui/`. `StaticFiles` serves `/ui/index.html` without that header by default, so browsers can retain a stale shell that still references old asset filenames after a rebuild.
- Vite alignment: current settings are correct (root at `apps/ui`, `base: "/ui/"`, `build.outDir: "dist"`). If these drift, the earlier Rollup resolution error and stale build problems reappear.

### Remediation plan (implemented next)
1) Reorder preview API routes so `GET /api/run/current` is declared before `GET /api/run/{run_id}`.
2) Add lightweight HTTP middleware to set `Cache-Control: no-store` when serving the UI shell via `/ui`, `/ui/`, or `/ui/index.html`. Hashed assets remain cacheable.
3) Keep Vite config stable (no changes required now). Ensure `apps/ui/index.html` continues to reference `/src/main.tsx` with `root` set to the `apps/ui` directory.

### Update — React Error #31 (object rendered)
- Symptom reproduced after build+preview: React error #31 mentions an "object with keys {runId, generatedAt, dryRun, source, headline, form, resume}".
- Root cause: the pipeline writes a structured preview object into `run.json` at `preview.summary` (via `RunStore.record_preview_summary(summary=SummaryPayload.to_preview_payload())`). The UI expects `preview.summary` to be a string. Rendering the raw object in `<p>{summary}</p>` triggers error #31.
- Fix applied: backend coercion in `apps/preview/main.py` `_sync_persistent_state()` now converts a dict `preview.summary` into a human-readable string (title/company/location, form counts, resume status), falling back to pretty-printed JSON when needed. This guarantees the UI receives a string and prevents React from trying to render an object.

### Verification checklist (post-fix)
- `GET /api/run/current` returns 200 with the active run and never matches the `{run_id}` handler.
- Navigating to `/ui/` after a rebuild picks up the fresh index shell; assets load successfully and React error #31 does not reoccur.
- `pnpm run build` outputs `apps/ui/dist` with `/ui/`-prefixed asset URLs inside `index.html`.

### Notes
- No additional files or secrets were needed beyond the repo. If we later externalize the UI to a different mount path, update both Vite `base` and the FastAPI `app.mount()` path to keep them in sync.
